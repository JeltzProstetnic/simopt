- [x] **SIM-81** **MersenneTwister is now a Mersenne Twister — DONE 2026-08-26, test-first, pinned to the published vector.** Reference initialisation (`mt[i] = 1812433253·(mt[i−1] ^ (mt[i−1] >> 30)) + i`), index starting at 624 so the first draw twists, and the reference tempering applied to the output only. `NextUInt()` made public because the only conclusive test is agreement with the published raw-word vector, and `NextInteger()` masks bit 31 away — hiding exactly the defect being fixed. Pinned against the canonical seed-5489 sequence plus two other seeds, generated by an independent implementation. Suite 914 → 922, zero regressions and zero re-baselined constants. Full measurements: `docs/plans/2026-08-26-sim-81-mersenne-twister.md`. **Three findings worth carrying.** (1) **The repaired defect is real and large but local:** KS on the first block (n=624) goes from √n·D = 12.4989 to 0.6686 against a critical 1.62762, and bit 31 from 0/624 draws to 302/624. (2) **The backlog's expected evidence did not materialise and this entry previously implied it would:** at n = 1,000,000 *both* generators pass uniformity comfortably (0.7746 old, 1.0327 new) and a low-3-bit chi-square passes for both — the first-block defect dilutes to invisibility in a large sample, and tempering's benefit is 623-dimensional equidistribution that no 1-D frequency test can see. This is a **conformance fix, not the repair of a wrong answer**, and must not be described as one. (3) **Both generators pass the whole analytic battery on all four seed sets tried**, but mean |error|/half-width falls from 0.421 to 0.302 and — more interestingly — the old generator's figure barely moves across seed sets (0.399–0.453) where the new one varies as noise should (0.139–0.479). A quantity that should fluctuate and doesn't suggests a systematic component, plausibly cross-stream correlation since per-node seeds are XOR-derived from one base seed. Four seed sets cannot settle it; **SIM-96's coverage meta-test is what would**, which is now a second reason to build it. **Left open deliberately:** `R250_521`, `LinearCongruentialGenerator` and `SubtractiveCongruentialGenerator` have never been checked against any reference vector and nothing here speaks to them — see SIM-98. - [x] **SIM-89** **The MCP head could not build or run a single model — three independent defects, all shipped, all invisible.** Found 2026-08-26 by writing the first smoke test against `create_model`. **DONE, test-first.** (size: M) — **P0**
  1. `ModelRegistry.CreateNegExp` handed `Random<T>` an already-initialised distribution, which its constructor rejects outright (`Random.cs:75`) — so **every** `create_model` call threw. Fixed by configuring without initialising and moving seeding to the engine's own `SeedID` mechanism, supplied at construction (the `SeedID` setter refuses to run after the entity has seeded itself). Per-node streams are now a pure function of (topology seed, node id) and are independent of node ordering — a strictly stronger property than SIM-62 delivered, and one an LLM-emitted node list needs.
  2. `Model.Reset` enumerated the live `items` dictionary while an auto-starting source created an entity into it, throwing `Collection was modified` from inside the reset. Fixed by snapshotting, the same remedy SIM-58 applied to `ResourceManager.Reset`. **Engine-level, affects every auto-starting model, not just MCP ones.**
  3. `ModelRegistry` never registered the buffer→server kick handler (`if (server.Idle) server.Start()`), which every other builder in the repo does. Items entered the queue and stayed there: the run completed "successfully" and every sink reported zero.
  **Why none of this was noticed:** `SimulationTools` wraps every call in a catch-all that serialises the exception into an `error` field, so a completely broken build path returns well-formed JSON and reads, to a caller, exactly like a working tool rejecting a bad model. The lesson is recorded in the new tests: assert on the *absence of an error field* and on real post-run numbers, never on the call completing.
- [x] **SIM-90** **Entity identity was destroyed at every server — DONE 2026-08-26, and the causal story first recorded here was WRONG.** The defect and both consequences were real: `ModelRegistry` left `Server`'s default product generator in place, which returns `new TProduct()` with a **null Identifier**, and `Buffer.Put` keys on that Identifier — so a two-stage MCP topology threw `ArgumentNullException` at simulated time 1.170 with zero entities delivered, meaning **every multi-stage topology was unbuildable** and end-to-end cycle time was unmeasurable. **The correction:** this entry previously claimed `createProduct: m => m[0]` could not be applied because the auto-continue repeater re-entered `StartWorking` and cleared `activeMaterial` before the deferred factory ran. That is false on two counts, both measured: the factory is invoked **exactly once, at raise time, before** `InternalFinishedHandler` clears the list; and the finish instance is raised **before** the repeater regardless of insertion order, because `Priority.CompareTo` compares `PriorityType` ahead of `AddedOrder` and finish carries `SimWorldBeforeOthers` against the repeater's `LowLevelAfterOthers`. The `IndexOutOfRange` actually observed was the **pre-SIM-91 phantom-finish-after-reset** path — a finish scheduled against material that `Server.Reset` then wiped — and commit `3279543` had already removed it hours earlier. On current main the obvious fix simply works: 495 factory invocations, 0 against an empty list, 492 entities through a tandem to the sink. **Shipped anyway:** the batch is snapshotted into the closure at scheduling time in both `StartWorking` and `StartFailing`, because the empty-list *class* is still reachable — `ClearActiveMaterial` scheduled mid-service leaves a pending finish with a count of 0 (measured). Unblocks SIM-63's cycle-time collector and SIM-64's Jackson network. (size: M) — **P1**
- [x] **SIM-91** **First run of a freshly built model diverged from all later runs — DONE 2026-08-26, root cause confirmed by measurement.** `Source.Reset` called `Start(0)`, which raises `EntityCreatedEvent` **synchronously**, from inside `Model.Reset`'s entity pass — so the t=0 arrival met downstream entities that had not been reset yet, and its fate depended on how the *previous* run had left them. Idle server ⇒ it pulled the entity and scheduled finish events into the freshly cleared calendar; `Server.Reset` then wiped `working` and the material but could not cancel those events, so they fired during the run and delivered a **phantom product**. Busy server ⇒ the entity waited in the buffer and `Buffer.Reset` destroyed it three lines later. **Both behaviours were wrong** — the first run invented an arrival, every later run silently executed the genuine one, and the disagreement (476/2862 against a stable 475/2859) is only how it surfaced. Fixed by deferring the zero-delay auto-start to a t=0 scheduled action, the same idiom `Server.Reset` already uses, so it fires after the reset completes against fully reset state. Pinned by a constant-distribution test whose expected count of 5 discriminates all three behaviours (4 = arrival destroyed, 5-with-different-event-count = phantom, 5-stable = correct). MCP-surface numbers legitimately move 475→476. Serves UN-009, UN-033. (size: M) — **P0**
